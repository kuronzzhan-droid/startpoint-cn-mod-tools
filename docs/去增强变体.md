# 去增强变体(content-only)——设计与操作

> 面向发包方(我们自己)。收方视角看 [`分享包收方指南.md`](分享包收方指南.md) 的「变体」一节。

对外分享时,同一批内容出两个变体:

- **full** —— 自服完整终态,含个人增强。
- **content-only** —— 只有内容(三自制角色 129999/139999/149999、15 把深渊武器
  8000101-8000115、700099 随机塔模式),**所有官方行回滚为官方 CDN 原值**。

工具:`wf_enhancement_policy.py`(策略与重建引擎)+ `wf_share_variant.py`(打包与声明)。

---

## 1. 为什么不能"抽 zip / 关 manifest 开关"

- `manifest.json` 的 `patches[].enabled` **不是运行时开关**:服务端 `cn-asset-graph.ts`
  只扫 `assets/asset-patch/active/` 目录建图,enabled 只被 `wf_publish` / `wf_release`
  当版本号地板用。真开关是 zip 在 `active/` 还是 `inactive/`。
- 中途停用某条边 → 下游边孤立,新装/落后客户端**静默搁浅**在断点(2026-07-18 链重锚事故同形)。
- 增强不是独立的包,是**烤在每一份全表快照里的行**。抽掉一张表 = 深渊武器/自制角色行一起没,
  客户端 C8601。

所以隔离只能发生在**对外打包处**,按行重建,不动我方自己的链。

## 2. 官方基准从哪来(关键)

**官方 CDN 归档,不是 store 备份。**

`.cdn/cn/archive-<root>-full/pinball-<base>-<seq>-<hex>.zip`(官方全量)+
`archive-<root>-diff` 里 **to 版本 ≤ 1.4.54 且 tag 不以 `mod` 开头**的官方增量,
按版本序重放,末次写入即官方原值。CN 官方链尾就是 **1.4.54**——之后的边全是我们自己发的
(tag 一律 `mod*`),这条分界线在文件名上就能判。

store 里的 `.bak-wfmod-*` 备份**不能当基准**:

| 备份 | ability 行数 | 说明 |
|---|---|---|
| `.bak-wfmod-gui-20260706-071317` | 2972 | 恰好等于官方原值(sha256 `d296bee4…`) |
| `.bak-wfmod-balance-20260709-003745` | 2652 | 平衡套件自己的"锁定基准",**已带它前一轮的改动** |

`wf_balance_suite` 用后者做重建基准是对的(它要保住用户手改),但拿它当"官方原值"会
少 320 行、并把一轮增强当成官方。本引擎一律用官方归档。

**交叉验证**:引擎解析出的官方 `ability_soul`(38313 B / `70dd53d7…`)与
`equipment_enhancement_ability`(3640 B / `b9aa82f7…`)与
`build_abyss_weapon_balance_patch.py` 里独立钉死的常量逐字节一致。这两条哈希写进了
`PINNED_BASELINES`,每次建索引都校验,对不上直接 `BaselineUnavailable` 停机。

## 3. 重建规则(三条,数据驱动)

对终态里的**每一个**条目:

1. **在 drop-list 里** → 丢弃。目前只有一条:白虎技能 DSL
   `battle/action/skill/action/rare4/white_tiger$white_tiger_2.action.dsl.amf3.deflate`
   (全链唯一被改写的官方资产表外文件;不下发 = 收方保留自己的官方原件)。
2. **官方基准里没有** → 原样保留(自制资产/自制行的载体)。
3. **官方基准里有且被改过**:
   - 是 orderedmap → **按行重建**:官方 key 取官方值;官方 key 双方都是嵌套 map 时递归
     (允许模式往官方行里**加嵌套子行**,如 `zone.treasure_cave_area` 的场地);
     live 里多出来的 key 原样追加在官方行之后;live 里被删掉的官方行**补回**。
   - 不是表 → 按 `--official-file-action` 处理:`drop`(默认)或 `revert`(回滚成官方原件下发)。

**不删任何新增行。** 新增行伤不到官方数据(是新 key),漏删远比错删安全;认不出归属的新增行
会在审计里单列("未识别的新增行"),等人工判定,而不是静默丢掉。

## 5. 用法

```bash
# 审计:当前链里到底有多少增强面(不产出任何文件)
python mod-tools/wf_enhancement_policy.py audit

# 预览两个变体(不落盘)
python mod-tools/wf_share_variant.py plan --anchor <收方链尾>

# 构建。--anchor = 收方当前链尾;外血统(版本号空间与我方无关)要加 --foreign-lineage
python mod-tools/wf_share_variant.py build --anchor 1.4.130 --foreign-lineage \
    --tag share0729 --min-server modes-20260714 \
    --server-feature rush-mode --client-patch five-in-one-v2

# 只要纯内容变体
python mod-tools/wf_share_variant.py build --variant content-only --anchor 1.4.130 --foreign-lineage
```

产物:`mod-tools/work/share_variant/<tag>/wfshare-<from>-to-<to>-<variant>/`,
内含三层 `archive-*-diff/`、`requires.json`(带 `enhancement` 字段)、`说明.txt`、`report.json`。

顺带:`wf_pack_consolidate` 也加了 entry 级排除(`--drop-logical` / `--drop-entry`),
用于整合时剔除**独立资产文件**。表不要用它——表要去增强只能走本引擎的按行重建。

## 6. 硬约束(工具已强制)

1. **我方自己的链零改动**:产物只写 `work/`(或 `--out` 指定的仓外目录);写进 CDN 根或
   `assets/asset-patch` 直接报错。
2. **已消费的 from-to 边严禁换内容重切**:锚定边若在我方可见图里已存在,直接拒绝构建;
   确认收方是外血统时用 `--foreign-lineage` 显式放行,报告里会留警告。
3. **两个变体的 zip tag 不同**(`<tag>` / `<tag>co`),收方混铺会被 `说明.txt` 明确警告。

## 7. 自检与测试

构建时**每个变体落盘后自检**,不通过就整体回滚、不留半成品:

- 产物条目集 == 计划条目集,无重复成员;
- content-only 再跑金样校验 `verify_content_only`:官方行逐行等于官方原值(允许官方行下多出
  嵌套子行)、官方行一个不少、drop-list 条目确实不在包里、
  `EXPECTED_CONTENT_ROWS` 里的模式/角色/武器行齐全(缺一即失败)。
  故意发局部内容包时用 `--no-content-expectations` 关掉最后一条。

自动化测试:`tests/test_enhancement_policy.py`(28 例)、`tests/test_share_variant.py`(22 例)、
`tests/test_pack_consolidate.py` 的 `DropListTest`(7 例)。全部用临时目录里的合成 orderedmap,
**不依赖真实 store / .cdn**,CI 可跑。

```bash
cd mod-tools && python -m unittest tests.test_enhancement_policy tests.test_share_variant
```
