# 发布事故复盘

本文适合准备打包补丁边、更新资产清单或同步客户端与服务端数据的改包维护者阅读。每次出包前逐条对照这些通用防呆教训，可以避免误删线上已有角色、卡死玩家热更链或静默回滚历史修复。

## 1. 整表投递前未核对键差集，发包变成静默删内容（`C8601`）

- **现象**：发布一版只改单个新内容的补丁后，原本正常的既有角色或技能在主城与编队界面集体报 `C8601`（指定的 Key 不存在）。
- **原因**：客户端热更的最小投递单位是整张 `orderedmap` 二进制文件，不存在「只更新某一行」的协议。只要待发表文件比线上当前终点少了几个键，或者键没少但大批键的内部记录条数比线上少，发布出去就是用残表整体覆盖线上全表。
- **怎么做**：始终基于当前补丁链终点叠加变更集（`python -m wf deliver`），严禁把早期本地工作区里的旧整表直接拿来重发；出包前强制比对新旧表的键集合与各键记录数。
- **怎么验证**：打包前运行 `python -m wf.studio.draft --view <视图名> key-diff --zip <交付目录中的common层.zip> --subject <角色ID>` 或 `python wf_publish_guard.py`（注：`wf_publish_guard.py` 需已配置含 `.cdn/cn/archive-common-diff` 的 `paths.server`，否则会报 `配置的 server 无法导出有效 CDN 根`）。预期看到线上已有键 0 缺失、无大面积记录缩减提示；一旦提示少键，立即中止打包并基于最新链终点重算变更。

## 2. 原地覆盖已发版本号或倒退版本号，导致热更失效与断链

- **现象**：发现刚发出的补丁有缺陷后，原地替换同版本号的压缩包或把目标版本号往回改，结果已更新的玩家拉不到修复，另一批玩家卡死在热更界面。
- **原因**：客户端热更检查器严格按「本地当前版本 -> 服务端目标版本」查找正向增量边。目标版本与本地版本相同时，客户端直接跳过下载（更新 0 个文件）；目标版本低于本地版本时，客户端找不到反向回退边而彻底失联。
- **怎么做**：版本号必须严格单调递增。任何已对外发布的坏包绝不原地改包、绝不回退版本号，一律再往前递增一个新版本号发布正向修复边。
- **怎么验证**：对交付产物运行 `python -m wf check <delivery-manifest.json>`。预期版本号严格递增且从基线版本到新终点连续可达；若存在重号或断边，作废该包并递增序号重出。

## 3. 热更表与客户端内置表撞键（`C7051`）或用 CDN 强盖内置图集（`C8004`）

- **现象**：补丁发出后所有玩家启动游戏即死在 `C7051`（键重复），或者替换战斗公共界面图标后进战斗必崩 `C8004`。
- **原因**：客户端内置包 `bundle.zip` 含有一批 `*_iosbundled` 基础表，启动合并时要求与 CDN 下载表键集合完全不相交，两边出现同一个键就会直接抛 `C7051`。同理，封在内置包里的战斗公共图集（如 `battle/common/layer1`）不支持仅靠 CDN 散包覆盖。
- **怎么做**：新增表键前先与内置包键表做交集排除；涉及内置表既有键或内置核心战斗图集的改动，走客户端底包更新而不是纯 CDN 补丁。
- **怎么验证**：运行 `python -m wf.studio.draft bundle-check --apk <客户端APK> --delivery-dir <交付目录>`。预期输出 0 个内置撞键冲突；若有撞键提示，把冲突键移出 CDN 变更集。

## 4. 三层资产平铺撞序号、漏带层前缀或单包超出 5 MiB 上限

- **现象**：同批发布的立绘大图与通用表压缩包在平铺目录里互相覆盖丢失，命令行漏打包了 `medium` / `android` 层文件，或交付门禁拒收超大压缩包。
- **原因**：资产按 `common`（表与脚本）、`medium`（立绘大图）、`android`（平台专属纹理）分三层存储，在扁平补丁目录共存时若共用同一序号会互相顶替；只按通用表模式抽包而不声明 `medium:` / `android:` 前缀会漏掉跨层资产；且公开补丁链硬性限制单个补丁 ZIP 不得超过 `5 MiB`。
- **怎么做**：统一用 `python -m wf deliver <修改包.json> --baseline-manifest <manifest.json> --base-store <store目录> --out <输出目录>` 自动按三层分配唯一序号并检查包体积；大批量高清立绘拆成多条连续补丁边分批交付。
- **怎么验证**：运行 `python -m wf check <delivery-manifest.json>`。预期三层文件哈希全部对账通过且每个 ZIP 均 `<= 5 MiB`；若有超限包，拆分变更集后重打。

## 5. 角色独立包工作区快照滞后，重发旧包把线上热修静默回滚

- **现象**：早先已在共享表修好的数值或补加的关联行，在某次重发单个角色工作区包之后莫名变回了旧版，或未进认领清单的新行被漏发。
- **原因**：角色独立包内部保存的是建包当时的整表快照，合并时按包清单里的 `outer_keys` 认领并覆盖目标键。如果线上直接热修了共享表却没回灌到角色工作区，下次重发该角色包就会拿旧快照盖掉线上新数据；反过来新增了跨表键却没写进认领清单，打包时就会漏收。
- **怎么做**：线上热修共享表后立即运行 `python wf_pack_backfill.py --table <逻辑路径> --apply` 把最新表字节原地回灌进各角色工作区；新增关联表键时同步补齐该包的键认领列表。
- **怎么验证**：重发前先跑 `python -m wf.studio.draft rehearse --delivery-dir <交付目录> --server local` 预演合并，再跑 `python -m wf.studio.draft --view <视图名> key-diff --zip <交付目录中的common层.zip> --subject <角色ID>` 逐键查看字段差异。预期线上热修字段无倒退、新键全部命中；发现旧值回滚则先做回灌。

## 6. 写错表行压缩格式，或把磁盘分片哈希路径当逻辑路径二次哈希

- **现象**：新表发出去后客户端刚读表就解析崩溃，或者热更包正常下发但游戏里完全读不到新资产。
- **原因**：不同 `orderedmap` 的行存储格式不同（有的是 `78 da` / `78 9c` 开头的 `zlib` 压缩块，有的是明文 UTF-8 CSV），混用编解码器会直接写坏二进制表；另外数据目录磁盘上的 `<2位十六进制>/<38位十六进制>` 文件名已经是加盐 SHA1 结果，若误当成逻辑路径再算一次哈希，客户端永远查不到这个地址。
- **怎么做**：严格通过仓库内置的表编解码器读写表数据，不手拼裸字节；所有变更集与打包命令一律填写如 `master/ability/ability.orderedmap` 的明文逻辑路径。
- **怎么验证**：运行 `python -m wf check <修改包.json>`。预期表解码往返校验与逻辑路径格式检查全部通过；若提示疑似哈希分片路径或解码异常，改回明文逻辑路径并按标准编解码器重写。

## 7. 先发引用后发图集导致中间态闪退，或 `CRLF` 换行破坏服务端镜像对账

- **现象**：分包更新期间玩家点开商店即崩 `C8004`，或者客户端与服务端文本肉眼完全一致但交付回执一直报哈希不匹配。
- **原因**：表行先指向了尚未下发的新图集子纹理，客户端处于有表无图的中间态必崩 `C8004`。此外 Windows 环境默认写文本会产出 `CRLF`（`\r\n`），而服务端 JSON 镜像与交付回执统一按 `LF`（`\n`）字节计算哈希。
- **怎么做**：新增图集子纹理与引用它的表行要么放进同一补丁边原子下发，要么先发图集边、后发表边；所有 JSON 与服务端镜像强制使用 `LF` 换行写入；带全局影响的服务端新玩法开关在随包上线时默认设为关闭。
- **怎么验证**：依次运行 `python -m wf check text <快照.json>`（或 `python -m wf text check <角色ID> --tip <版本号> --server-text <服务端目录>/assets/cdndata/character_text.json --rank-text <服务端目录>/assets/cdndata/character_text_rank_p5b.json`）与 `python -m wf check <delivery-manifest.json>`。预期镜像对账与纹理引用检查全部通过；若报字节哈希差异，统一转换为 `LF` 后重新生成。

## 8. 漏查客户端底座能力清单，向旧端下发扩展词条（`C7050` / `U_1d93f4`）

- **现象**：高版本补丁客户端上测试通过的扩展词条或双形态角色，下发后导致未升级底座的玩家启动即崩 `C7050` 或协力爆图集。
- **原因**：编号大于 `723` 的扩展词条、DSL 完整伤害类型改写码等特性依赖客户端代码补丁提供构造器；原版或低版本底座没有对应枚举槽位，读表时直接抛未知构造异常。
- **怎么做**：先从目标客户端提取支持能力集 `python -m wf apk provides <客户端包> --output <provides.json>`，打包交付时带上 `--provides <provides.json>` 让工具自动核验能力边界。
- **怎么验证**：运行 `python -m wf check compat --requires <requires.json> --provides <provides.json>`。预期输出完全兼容且返回码为 0；若报能力缺失，改回原版兼容词条或要求先升级客户端底座。

## 9. 共用全局待发队列引发并发串包，以及卫生与门禁「假绿灯」

- **现象**：同时处理两项修改时，后打的包把前一项还没改完的半成品表带上了线；或者门禁脚本显示通过，却漏放了违规数据或本机敏感路径。
- **原因**：多个任务共用单一全局待发文件并整表覆写时极易互相污染；部分旧检查逻辑存在未覆盖的新列盲区，不拿坏样本反测就发现不了假绿灯；公开提交若靠整文件豁免绕过卫生脚本则容易泄露本机路径或内网信息。
- **怎么做**：每个任务使用独立草稿与变更集（`changeset.json`）隔离交付；新增门禁规则后先喂一条故意写坏的样本确认能拦住；公开文档与代码绝不添加整文件卫生豁免。
- **怎么验证**：先对构造的违规样本运行 `python -m wf check <违规样本>` 确认非 0 拦截，再对正式包运行确认返回 0；最后在仓库根目录运行 `python scripts/check_no_hardcoded_paths.py`（装有 Git Bash 时再跑 `bash scripts/check-hygiene.sh`），预期输出干净无任何路径或敏感项告警。
