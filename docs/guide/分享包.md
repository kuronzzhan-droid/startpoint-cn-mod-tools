# 分享包

本手册面向 Windows 新手。分「我是收包方」和「我是发包方」两部分，说明如何安全检查、导入、部署别人的分享包，以及如何把自己的内容打包分享给别人。

## 一、动手前必懂的 3 条保命规则

### 1. 先分清「同血统跟链」还是「外血统」（最关键！）

游戏里的核心主表（`orderedmap`）在传统热更 ZIP 里是**整张表替换**的：
- **同血统（跟链）**：你的服务端原本就跟着发包方的资源版本链走，自己没有改过主表——可以直接按版本顺序接上热更包。
- **外血统**：你自己的服务端里已经改过别的自制角色、武器或词条——**绝对不能把别人传统分享包里的 `archive-common-diff/*.zip` 直接拷进你的热更目录**！整表覆盖会把你自己的自制内容全部抹掉。外血统收包请走下文的**收方路线 A（`wf_release_v1` 隔离导入与接管）**或**收方路线 C（按行/键合并）**。

### 2. `content-only` 与 `full` 两个变体绝不能混装

发包方通常会提供两种变体：
- **`content-only`（纯内容变体）**：只含新增角色、武器或副本内容，官方原有角色全部剥回官方 `1.4.54` 原始数值。
- **`full`（含增强变体）**：除了新内容，还包含发包方自己改的全角色数值增强。

**二选一即可，绝对不能把两个变体的 ZIP 同时放进同一个 CDN 目录**（两边占用同一段版本号但文件内容不同，客户端热更必报校验错误）。

### 3. 先看清客户端档案要求

收包前先看包内的 `requires.json`、`share-manifest.json` 或说明文件，确认你的客户端 APK 是否满足所需能力（详见 [`客户端补丁与APK.md`](客户端补丁与APK.md)）。未打对应补丁的客户端拉取扩展词条后会闪退或词条失效。

## 二、我是收包方：收到分享包怎么处理

| 你收到的包是什么情况 | 推荐走哪条路线 |
|---|---|
| 收到 `.wfshare` 包，我是外血统服务端、想安全检查包内内容，或想把里面的角色接管过来微调 | **收方路线 A：`wf_release_v1` 只读体检与隔离接管（最安全）** |
| 收到同血统增量分享包，我没改过自己的表，只想原样跟链放到服务端 | **收方路线 B：同血统三层归档直接部署** |
| 收到离线武器/副本补充包（`.zip`）或带 `asset-manifest.json` 的纯角色媒体包 | **收方路线 C：按行/键或带前像预检无损合并** |

---

### 收方路线 A：用 `wf_release_v1` 体检、隔离导入与接管角色（推荐）

这套工具全程不触碰你的现网 `store` 和服务端，且在导入时会自动隔离包内任何可执行脚本、绝不运行它们。你也可以运行 `python -X utf8 wf_release_ui.py --open` 在本地网页工作台中点选完成以下步骤。

#### 第 1 步：不解压落盘，先做只读安全体检

- **做什么**：在工具仓根目录打开 PowerShell，运行：
  ```powershell
  python -X utf8 -m wf_release_v1 inspect-share --share <收到的分享包.wfshare> --json
  ```
- **预期看到什么**：终端输出结构化 JSON，列出该分享包的变体模式（`full` 或 `content-only`）、版本跨度、包含的文件清单以及潜在风险提示，退出码为 `0`。
- **不对怎么办**：若报归档损坏或路径越界（Zip Slip），说明该压缩包不合规，立即丢弃不要解压。

#### 第 2 步：拆解导入到本机隔离目录

- **做什么**：指定一个新的空目录作为隔离导入区（如包内需要映射文件，可加 `--mapping <映射.json>`）：
  ```powershell
  python -X utf8 -m wf_release_v1 import-share --share <收到的分享包.wfshare> --output work/share_import/<包名> --json
  ```
- **预期看到什么**：命令退出码为 `0`，内容被规范化拆解到 `work/share_import/<包名>`；若缺少完整映射，JSON 中的 `mappingStatus` 会提示还需补充哪些映射项。
- **不对怎么办**：按输出提示补齐 `--mapping` JSON 后重新导入到新的空目录。

#### 第 3 步：接管包内角色（可选检出编辑与重新封口）

- **做什么**：参照 [`examples/legacy-character-adoption.rolf.json`](../examples/legacy-character-adoption.rolf.json) 编写一份角色所有权接管配置 `<接管配置.json>`（声明该角色独占的角色 ID、表键和资产路径），把导入内容转为受契约保护的角色工作区：
  ```powershell
  python -X utf8 -m wf_release_v1 adopt-character --imported work/share_import/<包名> --config <接管配置.json> --output work/adopted/<角色名> --json
  ```
  如果你还想微调这名角色的文案或数值，可检出可编辑副本，改完后再重新封口：
  ```powershell
  python -X utf8 -m wf_release_v1 checkout-character --workspace work/adopted/<角色名> --output work/edit/<角色名> --package-version 1.0.1 --json
  # （在此修改 work/edit/<角色名> 内的受管角色数据，或用 wf_preview_2d.py 预览动画）
  python -X utf8 -m wf_release_v1 seal-character --workspace work/edit/<角色名> --json
  ```
- **预期看到什么**：`adopt-character` 与 `seal-character` 均返回成功 JSON，所有文件哈希与表键所有权边界校验通过。
- **不对怎么办**：报所有权越界时，检查 `<接管配置.json>` 是否把不属于该角色的公共键写了进去。

#### 第 4 步：按你自己的服务端版本链尾生成覆盖层或发行包

- **做什么**：用封口后的工作区（`work/adopted/<角色名>` 或 `work/edit/<角色名>`），按**你自己服务端当前的资源链尾版本**（`<你的当前版本>` → `<下一版本>`）生成 Content Sync 补丁覆盖层：
  ```powershell
  python -X utf8 -m wf_release_v1 build-overlay --workspace work/adopted/<角色名> --from-version <你的当前版本> --target-version <下一版本> --output work/overlay/<角色名> --json
  ```
- **预期看到什么**：在 `work/overlay/<角色名>` 下生成三层增量归档与 `patch-manifest.json`。随后可按 [`发布与回滚.md`](发布与回滚.md) 的路线 2 打包 `.wf-release.zip` 并用 `plan-install` / `install` 安全安装。
- **不对怎么办**：若报版本格式非法，确认 `--from-version` 与 `--target-version` 均为 `1.4.<数字>` 且目标版本高于起始版本。

### 收方路线 B：同血统三层归档直接部署到服务端

当你确认自己与发包方是**同血统跟链**，且已选定 `content-only` 或 `full` 其中唯一一个变体时，按你的服务端分支类型部署（详见 [`分享包收方指南.md`](../分享包收方指南.md)；本机外部服务端实装标「未实测」）。

#### 第 1 步：核对起点版本号与分包完整性

- **做什么**：查看待拷入的 `pinball-<起点版本>-<终点版本>-<序号>-<标签>.zip` 文件名。
- **预期看到什么**：
  - `<起点版本>` 必须**严格等于**你服务端 CDN 目前的最高链尾版本；
  - 跨越很多小版本的单条整合边（如 `1.4.54 → 1.4.300`）或因单包 5 MiB 上限拆出的 `-1-`、`-2-` 多序号包都属于正常现象，同版本段的所有序号分包必须全部保留。
- **不对怎么办**：如果 `<起点版本>` 和你当前链尾对不上，说明中间缺了前置边或锚点不对，**不要硬拷**，联系发包方按你的链尾 `--anchor` 重新出包，或改走路线 A。

#### 第 2 步：按三层目录放入 CDN 并区分服务端类型同步

- **做什么**：
  1. 将包内 `archive-common-diff`、`archive-medium-diff`、`archive-android-diff` 三个子目录下的 ZIP 分别拷入你服务端 `.cdn/cn/` 下对应的同名三个子目录（**严禁把三层文件合并丢进同一个文件夹**）。
  2. 按你的服务端类型执行对应操作：
     - **主线动态扫链服务端**：**不要**把包里的 `dev-catalog/` 或 `EntityLists/` 拷进主线服务端；若包内带自定义玩法 `modes.d/`，将模式配置放入服务端对应目录并在 `modes-allowlist.json` 核对登记 SHA-256 后重启服务端。
     - **上游 `dev`（`content:sync` 启动前编译）服务端**：`dev` 扫描器要求每个版本步三层都有文件且清单齐全。拷入归档后，可在工具仓运行以下命令体检并生成 `dev` 清单：
       ```powershell
       python wf_dev_catalog.py --cdn-root <服务端.cdn/cn目录> heal-layers
       python wf_dev_catalog.py --cdn-root <服务端.cdn/cn目录> audit
       python wf_dev_catalog.py --cdn-root <服务端.cdn/cn目录> emit
       ```
       （若 `heal-layers` 干跑提示缺层占位包，按终端提示补齐后再跑 `emit`，随后在服务端目录执行其 `content:sync` 并重启服务端。）
- **预期看到什么**：`wf_dev_catalog.py audit` 无断链或缺层报错，服务端重启后客户端可正常拉取热更。
- **不对怎么办**：客户端卡热更或报校验失败时，第一时间检查是否误把 `full` 和 `content-only` 两套 ZIP 混放在了一起。

### 收方路线 C：合并离线内容补充包或纯角色媒体包

#### 场景 1：合并离线武器/模式补充包（`wf_offline_pack_apply.py`）

- **做什么**：先生成只读合并计划并在内存中干跑（`--dry-run-apply`），确认零冲突后再执行落盘与发布：
  ```powershell
  python wf_offline_pack_apply.py plan --pack <离线补充包.zip> --out work/offline_plan.json --dry-run-apply
  python wf_offline_pack_apply.py apply --plan work/offline_plan.json --pack-id <计划中的pack_id>
  python wf_offline_pack_apply.py publish --plan work/offline_plan.json --pack-id <计划中的pack_id>
  ```
- **预期看到什么**：`plan` 阶段清晰列出新增与变更键且无未授权覆盖报错；`apply` 自动备份原表后写入；`publish` 铸造本机热更边（本机实发标「未实测」）。
- **不对怎么办**：`plan` 报键冲突或缺少门禁授权时，不要强行 `apply`，先检查 `work/offline_plan.json` 中的冲突行明细。

#### 场景 2：接收精确角色媒体资产包（`wf_share_assets_receive.py`）

- **做什么**：先**不加** `--apply` 做整包冲突预检，检查无冲突后再加 `--apply` 写盘：
  ```powershell
  python wf_share_assets_receive.py --package <媒体包路径> --store <数据包upload目录> --output work/media_preflight
  python wf_share_assets_receive.py --package <媒体包路径> --store <数据包upload目录> --output work/media_apply --apply
  ```
- **预期看到什么**：`work/media_preflight/preflight.json` 中无冲突项；`--apply` 完成后在 `work/media_apply` 下自动留存 `before/` 覆盖前原件备份与 `journal.jsonl` 事务日志。
- **不对怎么办**：若 `preflight.json` 报告共享依赖冲突，停止 `--apply`，先核查冲突的公共贴图或音频路径。

## 三、我是发包方：怎么打包分享给别人

对外发包有两条底线：**不要把你个人的全角色魔改数值强塞给只要新角色的人**（用 `content-only` 剥离），**不要把对方客户端不支持的补丁码发过去导致对方闪退**（必填 `--client-profile`）。

### 第 1 步：审计当前链上的个人增强改动

- **做什么**：在工具仓根目录运行增强策略审计（默认以官方 `1.4.54` 归档为唯一官方基准）：
  ```powershell
  python wf_enhancement_policy.py audit
  ```
- **预期看到什么**：终端列出当前链终态中哪些表行属于“官方角色个人增强”（将在 `content-only` 变体中自动剥回官方原值），哪些属于“新增自制内容”（保留下发）。
- **不对怎么办**：若提示找不到官方 `1.4.54` 基准或 CDN 路径，先检查 `profiles/local.json` 中的 `cdn_dir` / `server` 配置，或运行 `python wf_enhancement_policy.py baseline` 校验基准索引。

### 第 2 步：（可选）把多段零碎历史热更边合并去重

- **做什么**：如果你只想把某一段历史增量 ZIP 合并成干净的单条边（不剥离表行，只去文件级冗余），依次运行 `list`、`plan`、`build`（`--tag` 只能用纯小写字母和数字）：
  ```powershell
  python wf_pack_consolidate.py list
  python wf_pack_consolidate.py plan --from-ver <起点版本> --to-ver <终点版本> --tag <纯小写字母数字标签>
  python wf_pack_consolidate.py build --from-ver <起点版本> --to-ver <终点版本> --tag <纯小写字母数字标签>
  ```
- **预期看到什么**：产物只写进 `work/pack_consolidate/<标签>/`（单包自动按 ≤ 5 MiB 拆分），完全不改动你现网的 `.cdn` 目录。
- **不对怎么办**：如果你不仅想合并边，还需要把表里的个人增强剥回官方值，请跳过本步，直接用第 3 步的 `wf_share_variant.py`。

### 第 3 步：按收方客户端档案构建 `content-only` / `full` 分享包变体

- **做什么**：先问清楚**收包方用的是哪一档客户端 APK**（如 `official`、`test-v34`、`test-v35e`，**千万不要填你自己的 `local-mumu`**！），以及收包方是同血统还是外血统（外血统可加 `--anchor <收方当前链尾> --foreign-lineage`）。先跑 `plan` 预演，无误后跑 `build`：
  ```powershell
  python wf_share_variant.py --client-profile <收方客户端档案名> --variant content-only --tag <纯小写字母数字标签> plan
  python wf_share_variant.py --client-profile <收方客户端档案名> --variant content-only --tag <纯小写字母数字标签> build
  ```
  *(注：如果不写 `--variant content-only`，工具默认会同时产出 `full` 和 `content-only` 两个子目录供收方二选一；如果你只发局部内容、不含全套深渊武器/称号，按需加上 `--no-content-expectations`。)*
- **预期看到什么**：`plan` 和 `build` 均通过客户端能力门禁，在 `work/share_variant/<标签>/` 下生成对应变体目录、按 ≤ 5 MiB 切分好的三层 ZIP、`requires.json` 与说明文件。
- **不对怎么办**：
  - 报能力门禁拒绝出包：说明你的自制内容用到了收方 `--client-profile` 不支持的客户端补丁机制；要么请收方升级到匹配的客户端档案，要么改掉超纲词条后再出包。
  - 若收方使用的是新一代 `wf_release_v1` 受管服务端，推荐直接按 [`发布与回滚.md`](发布与回滚.md) 路线 2 打包 `.wf-release.zip` 并运行 `verify` 校验后发给对方。
